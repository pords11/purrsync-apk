# Database Design

See the full diagram: **`assets/erd_diagram.svg`**

PurrSync uses **Cloud Firestore**, a NoSQL document database. There are no enforced foreign
keys or joins — relationships are modeled by storing the parent's document ID as a plain
string field on the child document, and the application code (`FirebaseService`) is
responsible for filtering by that field.

## Indexes
- `cats`: single-field index on `userId` (default, automatic).
- `weight_logs`, `vaccines`, `vet_visits`: composite index on `(catId, <date field>)` is
  required because each query both filters by `catId` and orders by a timestamp field
  (`date`, `dateGiven`, `visitDate` respectively). Firestore will prompt for these
  composite indexes the first time each query runs against a fresh project — accept the
  console's "create index" link if you see a `FAILED_PRECONDITION` error in testing.

## Required Firestore Security Rules (minimum)
```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{userId} {
      allow read, write: if request.auth != null && request.auth.uid == userId;
    }
    match /cats/{catId} {
      allow read, write: if request.auth != null;
    }
    match /weight_logs/{id} {
      allow read, write: if request.auth != null;
    }
    match /vaccines/{id} {
      allow read, write: if request.auth != null;
    }
    match /vet_visits/{id} {
      allow read, write: if request.auth != null;
    }
    match /api_test_logs/{id} {
      allow read, write: if request.auth != null;
    }
  }
}
```
These rules are intentionally simple (any authenticated user may read/write any document in
these collections) to keep the midterm scope manageable. A production version should
additionally check `resource.data.userId == request.auth.uid` (directly on `cats`, and via a
`get()` lookup on the sub-collections) so one user cannot read or modify another user's
cats. This tightening is listed as a remaining item in `docs/09_Completed_and_Remaining_Features.md`.
